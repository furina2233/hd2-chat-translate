# 接入依据

资源型 HD2SDK 用于 archive、网格、材质等模组开发，没有公开的运行时聊天替换 API。当前插件通过 Bingus Shared Loader 加载 Lua addon，用 LuaJIT FFI 校验固定游戏构建并接入原生聊天控件，网络请求由自带 WinHTTP DLL 完成。

## 已核验的游戏构建与正文路径

适配 Steam build `25480438`、EXE `1.8.46015.0`，磁盘 `game.dll` SHA-256 为 `2e2c3b7c2500646dadd5f2b4c6e0504dbb7e7896139f64cddc0d1813c718f51e`，PE timestamp `1790161983`、SizeOfImage `74727424`。启动时检查这些标识、代码节范围和已知签名；不匹配时停止回写。

已采集的短代码窗口及固定文本观察确认：

- 全局槽 `game.dll+0x346D538` 指向根对象；事件环从 `root+0x4F7080` 开始，64 项、步长 `0x4B4`，正文在每项 `+0xB4`，容量 `0x400`。
- 聊天 manager 为 `root+0x14498`，64 个控件槽从 manager `+0x4390` 开始，步长 `0x3D8`。不假定控件槽与事件槽始终同索引。
- 控件正文 key 为 `0x7518C954`。属性 map 在控件槽 `+0x220`；count 位于 map `+0x158`，entries 从 `+8` 开始，步长 `0x18`，有界读取最多 14 项。
- 正文 wrapper 为 `game.dll+0x1441CA0`，参数为控件槽 `+0x110`、正文 key 和持久 UTF-8 字符串。下层 `0x143A1B0` 借用指针，不复制正文，因此译文不能使用短期缓冲区。

原生 setter 会更新目标属性的类型标记、缓存 hash 和正文指针。回读允许这三个字段按契约变化，其余属性仍需稳定；失败时不会重复调用 setter。

上述 RVA 只对匹配构建有效。扫描字节相同本身不能证明函数语义，实际接入还依赖固定消息、控件读回和用户画面验证。代码中的 `chat_probe` 资源身份保持不变，诊断/扫描内核保留供签名门禁及回归；早期采集脚本和发行包已清理。

## 多行文字与历史布局

2026-10-02 用户确认：双语正文增加行数后会与上一条消息重叠；收到新消息时，已重叠的消息整体上移，间距没有恢复。原回写只修改正文属性并核对字符串指针，没有执行聊天行创建时的测量和尺寸更新。

对三份匹配构建的既有诊断报告进行有界静态反汇编，确认了以下流程。没有据此调用游戏的新增消息函数，也没有将这些内部函数视为通用的公开 API：

| 位置 | 已核验的行为 |
| --- | --- |
| 行创建路径 `0x1860B00` | 写正文后测量子控件 `row+0x110`，按其两个浮点字段计算高度，再设置外层行尺寸 |
| 高度 helper `0x18610C0` | 完整函数与创建路径的测量、计算及设尺寸步骤一致，参数为同类型外层行对象 |
| 位置 wrapper `0x1860DA0` | 标志为 `0` 的完整分支直接设置位置，并将按值传入的两个 float 缓存到 `row+0x3CC`；标志为 `1` 的分支未完整核验 |
| manager `+0x13990` / `+0x139C0` | UI 历史下一空槽索引和计数，槽仍从 `+0x4390` 开始、步长 `0x3D8` |
| 原排列循环 `0x185F170` | 从新到旧累计各槽 `+0x10` 与 `+0x20` 浮点值的乘积及间隔常量；此函数还推进索引和计数 |
| 间隔常量 `game.dll+0x23C7554` | 原排列循环读取的 float；通过模块内受检读取取得 |

修复复用与创建步骤一致的高度 helper，只对本次已确认回写的行重新测量。随后按当前 `head`、`count` 计算 `slot=(head-i-1)%64`，使用已完整核验的直接定位分支更新历史行；保留历史索引、计数和其他消息的文字。原新增消息函数及位置 wrapper 的动画分支不参与回写。

首版布局包的字段校验读反了：`row+0x10` 实为高度，`row+0x20` 实为纵向缩放。匹配同一 DLL 指纹的 [ModOptionsMenu 控件常量与计算](https://github.com/CowboyBingus/ModOptionsMenu/blob/main/src/mod_options_menu.lua#L94) 定义高度偏移为 16、缩放偏移为 32；聊天构造及 helper 对子控件也使用相同的两个偏移。首版把大于 16 的正常高度套入缩放上限而拒绝回写，测试夹具也沿用了错误字段顺序。用户随后反馈英文消息不变化，新会话报告确认两次请求和译文均成功、两次回写均在预检阶段失败。现有报告没有具体失败分支，因此不能单凭该报告确认两次拒绝的字段值。修订版按正确偏移校验和测量，夹具与独立边界断言同步修正，并记录有界的失败阶段及几何量化值；页属性、分配范围和原生签名门禁保持有效。

新增调用需要匹配原有游戏指纹、正文 setter、完整高度 helper 及直接定位分支的代码签名。回写前有界读取并复核 UI 历史及行几何，确认目标槽仍在历史中；布局成功还需确认位置缓存和历史身份稳定。任何新 RVA 都只适用于上述固定构建。静态指令、假控件测试和缓存读回不能代替游戏画面验证。

## 系统通知

当前只接受正文 key `0x7518C954`、已证实的字符串类型、活动环内正文指针和事件 tag `0x1C12037F`；不同 tag 在模型请求前被拒绝。本次新增 `slot_event_filtered` 安全计数，区分类型过滤与空槽。已有有限代码窗口表明该 tag 由聊天历史处理路径写入，但不足以证明它专属于玩家聊天。

2026-10-02 用户将游戏语言改为英文后，确认系统通知没有被翻译且没有引发崩溃，随后要求停止本轮通知探索。保留现有门禁，没有新增关键词过滤、未经证实的类别映射或采集模式。该画面观察不等于模型请求计数验证。

## 验收与限制

2026-10-03 用户反馈启用模组后游玩期间持续掉帧。静态检查发现，原翻译循环在每次游戏更新后扫描最多 4 个控件槽，各槽多次执行受检内存读取和复核，调用量随游戏更新频率增长。模型 worker 空闲时使用条件变量等待，游戏线程的提交、轮询和取消使用非阻塞锁尝试；这些路径没有发现忙轮询或等锁。状态切换还会绕过报告间隔，翻译回写的一次更新可能多次同步写入并强制刷盘。

按用户选择，常规及基线扫描改为最多每 200 毫秒一个批次，模型响应按每个请求分别每 200 毫秒轮询；扫描与响应独立计时，长帧之后不补跑。保留每批 4 槽及 16 KiB 读取预算、双读、消息身份及回写门禁。普通报告最多每 5 秒更新，首次及停止报告即时；只有报告取消强制刷盘，仍完整写入、关闭临时文件后替换。离线假时钟测试用于确认工作量上限及异常处理，实际帧率改善需要在相同游戏场景比较启用与停用模组。

2026-10-02 固定中文试验确认原聊天行显示“聊天翻译测试成功”；随后独立版在 addon 与 loader 分槽部署时完成进程内模型请求，用户确认原聊天行变成中文，新会话报告记录提交、译文就绪和回写确认各一次，相关错误为零。合并包后续的 TOC 错误已修正，用户后续反馈英文界面下系统通知未被翻译且游戏没有崩溃。用户已看到双语正文并报告多行重叠；本次行高及历史布局修复仍需游戏内验收。之前的崩溃修复见 [修复记录](crash-analysis-2026-10-02.md)。

事件记录没有已证实的唯一 epoch，双读与绑定检查不能完全排除同槽快速复用且正文又相同。缓冲区保活、预算、队列、过期和回写前复核见 [使用说明](chat-standalone.md)。长时间游玩、多玩家连续消息、其他服务商和后续游戏构建未完成全面验收。
